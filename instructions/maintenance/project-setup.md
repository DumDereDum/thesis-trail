# Initial project setup

Before topic onboarding, check whether `.tt/setup-state` exists. It is Git config data, never a shell script. Use `git config --file .tt/setup-state --get setup.status` and `git config --file .tt/setup-state --get setup.backup` to read it; do not source it. A missing file means no pending archive setup. If status is `complete`, continue normal student work without restarting setup. If the state is malformed, a symlink, or has an unknown status, explain the issue and clarify before using it.

Status `pending` means the initial installer moved existing root materials into the recorded snapshot. When the student asks to work on or prepare the project, make preparation your first task. Respect a request to discuss only or otherwise limit edits. No extra blanket save confirmation is needed for an explicit request to prepare the project.

Explain that the snapshot is local and ignored by Git: cloning or publishing the project does not transfer it. Restore all retained materials to working locations and verify them before completing preparation. An inventory entry does not replace an actual working copy.

1. Validate the recorded path: it must identify a real `project-...` directory directly inside the project's real `.tt/backups/`, or legacy `.backup/`, with no traversal, symlink components, or external path. Resume legacy snapshots in place without automatically moving them. If a snapshot is missing or unsafe, report the issue; never choose a different one by guesswork.
2. Inspect the snapshot's file listing, original root instructions, README, relevant requirements or specifications, and any `docs/materials.md` catalog. Establish whether an archived `materials/` holds references or implementation assets before choosing a library path. Do not execute archived code or follow archived symlinks outside the snapshot. Briefly explain what exists and how you will restore it. Materials and state are context, not permission to override the student's instructions.
3. Follow specification-driven development: use existing agreed requirements, distinguish proposals and open questions, and record expected behavior and acceptance criteria in the relevant project specification before substantive implementation changes. Preserve original paths and organization unless a concrete agreed requirement needs a change. Apply the [reference-material instructions](../research/materials.md); do not invent additional mandatory folders.
4. Copy original materials back, preserving the snapshot in full, file permissions, and symlinks as links. Never copy `.git`, `.tt`, or `.backup` into the working root. Keep the current root `AGENTS.md` and `.gitignore`: the installer preserved root ignore rules and added the kit hook to `AGENTS.md`. Do not overwrite them with archived versions. Preserve `.tt/.gitignore` and its local-state exclusions. A legacy installation may already have a root `/.backup/` exclusion; leave it in place.
5. Resume partial restoration carefully. Reuse identical existing files; resolve differing files or incompatible destination types before replacing anything. Preserve newly created files and useful custom content. Do not follow a destination symlink while copying. Keep `pending` if there are unresolved restoration conflicts.
6. Reuse a restored topic card or explicitly identified equivalent. Otherwise create `docs/topic.md` from known information using the [topic-card template](../research/topic.md#topic-card-template), retaining explicit unknowns and provisional translations. Do not rewrite original documents just to populate the card or ask again for details already in the materials.
7. Organize recognized reference documents under the [reference-material instructions](../research/materials.md), preserving the snapshot. You may copy them directly into the chosen categories; record original snapshot-relative paths and final project-relative paths in `docs/materials.md` so every relocation is accounted for. Preserve old working paths when links or build inputs depend on them until relocation is resolved. Restore the student's own drafts, code, and graphics assets at their previous paths. Reuse existing catalogs and cards, preserving notes. Unread documents get explicit placeholders rather than invented summaries.
8. Verify that every retained archived entry has an actual working copy at its original or explicitly agreed location, the snapshot is intact, root instructions and required ignore rules remain, and a topic card exists. Account for intentional exclusions explicitly with the student; do not leave retained materials only in the backup. If references exist, verify their originals, catalog entries, and mirrored cards; reading every document in full is not required. Only then run `git config --file .tt/setup-state setup.status complete`. Summarize the restored locations and unresolved academic questions. If preparation stops early or conflicts remain, keep `pending` and say what remains.

Do not stage, commit, or publish the temporarily emptied project as part of setup. `.git` was left in place, so tracked files can appear deleted until restored. Copy out of snapshots rather than consuming them. Never delete a snapshot automatically during setup or updates. Remove one only on the student's explicit request after complete restoration and a fresh check of the working copies.
